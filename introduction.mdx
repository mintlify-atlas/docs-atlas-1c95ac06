`tracing` is a framework for instrumenting Rust programs to collect structured, event-based diagnostic information. Maintained by the Tokio project and published on [crates.io](https://crates.io/crates/tracing) under the MIT license, `tracing` does _not_ require the Tokio async runtime — it works equally well in synchronous programs, other async runtimes, and `no_std` environments.

## Why Tracing Instead of Plain Logging?

Traditional log messages record a _moment in time_: a single line of text written to stdout or a file. In asynchronous systems like Tokio — where thousands of tasks multiplex across a handful of threads — those flat log lines intermix, making it nearly impossible to follow the logic flow of any individual request.

`tracing` expands upon logging-style diagnostics by adding two critical dimensions:

- **Temporality** — a `Span` has a beginning and an end. It can be entered and exited by the flow of execution, and it can exist within a nested tree of similar spans. You can see _how long_ something took and _what was happening_ when it happened.
- **Causality** — events emitted inside a span are causally linked to it. You know that a `WARN` log line about a missing database row occurred _during_ the `handle_request` span for user ID 42, not just that it occurred at 14:32:07.

In addition, spans and events are _structured_: they carry typed key-value fields (integers, strings, booleans, anything implementing the `Value` trait), not just free-form text strings.

```rust
use tracing::{info, warn, span, Level};

let span = span!(Level::INFO, "handle_request", user_id = 42u64);
let _enter = span.enter();

info!(status = 200u16, "request completed");
warn!(retries = 3u32, "upstream was slow");
```

## Structured vs. Unstructured Diagnostics

| | `log` crate | `tracing` |
|---|---|---|
| Data model | Unstructured text messages | Typed key-value fields |
| Temporal context | None | Spans with enter/exit |
| Async-safe | N/A | Yes (via `#[instrument]`) |
| Filtering | Level + target string | Level, target, span context |
| Ecosystem | Vast | Growing rapidly |

`tracing`'s event macros (`trace!`, `debug!`, `info!`, `warn!`, `error!`) are intentionally syntax-compatible with the `log` crate, so migrating an existing project often starts with a simple find-and-replace on import paths.

## Workspace Structure

The `tokio-rs/tracing` repository is a Cargo workspace containing several focused crates:

| Crate | Purpose |
|---|---|
| [`tracing`](https://crates.io/crates/tracing) | Primary instrumentation API — macros, `Span`, `Event`, `Subscriber` trait |
| [`tracing-core`](https://crates.io/crates/tracing-core) | Stable core primitives (`span::Id`, `Event`, `Subscriber`, `Field`, `Dispatch`) |
| [`tracing-subscriber`](https://crates.io/crates/tracing-subscriber) | Ready-to-use `Subscriber` implementations including the `fmt` formatter |
| [`tracing-appender`](https://crates.io/crates/tracing-appender) | File appenders, rolling writers, and non-blocking output |
| [`tracing-attributes`](https://crates.io/crates/tracing-attributes) | The `#[instrument]` procedural macro attribute |
| [`tracing-error`](https://crates.io/crates/tracing-error) | `SpanTrace` — attach span context directly to error types |
| [`tracing-flame`](https://crates.io/crates/tracing-flame) | Generate flame graphs from span entry/exit events |
| [`tracing-log`](https://crates.io/crates/tracing-log) | Compatibility layer to consume `log` records as `tracing` events |
| [`tracing-journald`](https://crates.io/crates/tracing-journald) | Layer for recording events to the Linux `journald` service with structured data |
| [`tracing-futures`](https://crates.io/crates/tracing-futures) | Utilities for instrumenting `futures`, `Stream`s, and `Executor`s |
| [`tracing-serde`](https://crates.io/crates/tracing-serde) | Compatibility layer for serializing trace data with `serde` |
| [`tracing-tower`](https://crates.io/crates/tracing-tower) | Compatibility with the `tower` middleware ecosystem |
| [`tracing-mock`](https://crates.io/crates/tracing-mock) | Testing utilities for asserting on spans and events emitted by instrumented code |
| [`tracing-macros`](https://crates.io/crates/tracing-macros) | Experimental macros for emitting trace events (unstable) |

**Libraries** should depend only on `tracing` (or `tracing-core` for maximum stability). **Applications** add `tracing-subscriber` (and optionally other output crates) to actually collect and display diagnostics.
